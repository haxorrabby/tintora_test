# Tintora Production Deployment

## CI and local quality checks

GitHub Actions runs on pushes and pull requests with Python 3.12 and Node 22. It installs the development requirements, runs Ruff and Django checks, checks migration drift, runs pytest, and compiles Tailwind.

Run the same checks locally:

```powershell
python -m pip install -r requirements/dev.txt
npm ci
ruff check apps config
python manage.py check
python manage.py makemigrations --check --dry-run
pytest
npm run build
pre-commit install
```

The project tests use SQLite by default. Production uses PostgreSQL.

## English catalog build (gettext-free)

The English translation catalog is generated by project tooling rather than GNU
gettext, so no `gettext`/`msgunfmt` binaries are needed on the host or in CI:

```powershell
python tools/i18n/build.py     # writes locale/en/LC_MESSAGES/django.po and django.mo
```

`build.py` collects msgids from `{% trans %}`/`{% translate %}`/`{% blocktrans %}`
across every template plus Python string literals, merges the hand-curated
`tools/i18n/translations_en.py` (and the recovered second-pass
`tools/i18n/translations_missing.py`), and writes both `.po` and `.mo`. It exits
non-zero when any msgid is untranslated, so it doubles as the coverage check.
The compiled `django.mo` is committed and shipped in the image; `polib` is a
development-only dependency (see `requirements/dev.txt`).

Regression-verify both languages after changing templates or translations by
restarting the app (the catalog is cached per process) and requesting the `/es/`
and `/en/` variants of the same page.

## Server and secrets

Use an EU-hosted server and EU region for PostgreSQL, object storage, backups, and monitoring. Keep the application, database, media, and backups in the agreed EU data-residency boundary.

Create a production `.env` outside source control. Set at least:

- `DJANGO_SETTINGS_MODULE=config.settings.prod`
- `DEBUG=False`
- A unique `SECRET_KEY` generated by Django, at least 50 characters; never use the example or development key.
- A separate, stable `TOTP_ENCRYPTION_KEY`; generate it with `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`. Back it up securely. Changing it requires staff TOTP re-enrollment.
- A long random `POSTGRES_PASSWORD`; URL-encode reserved characters because Compose uses it in `DATABASE_URL`.
- `ALLOWED_HOSTS=tintora.es,www.tintora.es`
- `ADMIN_URL_PATH` set to a private, non-default path and optionally `ADMIN_ALLOWED_IPS` as comma-separated IPs/CIDRs.
- SMTP credentials, company fiscal details, Stripe/Redsys credentials, and `USE_S3=True` with private S3-compatible storage credentials.
- `SECURE_SSL_REDIRECT=True` and the correct database and Redis URLs.

Do not commit `.env`, database dumps, TLS keys, or cloud credentials. Review the production settings check before every release:

```powershell
python manage.py check --deploy --settings=config.settings.prod
```

Resolve every warning. In particular, Django rejects the example development `SECRET_KEY` for production use.

## TLS and DNS

1. Point `tintora.es` and `www.tintora.es` to the server and restrict inbound access to SSH, HTTP, and HTTPS.
2. Obtain certificates for both names with Certbot or the hosting provider, storing them at `/etc/letsencrypt/live/tintora.es/` as referenced by `deploy/nginx.conf`.
3. Configure automatic certificate renewal and reload Nginx after renewal.
4. Review the proxy headers, CSP resource hosts, admin IP allowlist, and `SECURE_PROXY_SSL_HEADER` for the actual load balancer topology.

## First production deployment

Build the production image and start PostgreSQL and Redis first:

```sh
docker compose --env-file .env -f docker-compose.prod.yml build
docker compose --env-file .env -f docker-compose.prod.yml up -d db redis
```

Apply migrations and collect static assets before starting the application and proxy:

```sh
docker compose --env-file .env -f docker-compose.prod.yml run --rm web python manage.py migrate
docker compose --env-file .env -f docker-compose.prod.yml run --rm web python manage.py collectstatic --noinput
docker compose --env-file .env -f docker-compose.prod.yml run --rm web python manage.py check --deploy --settings=config.settings.prod
docker compose --env-file .env -f docker-compose.prod.yml up -d web celery_worker nginx
```

The web process runs Gunicorn as the unprivileged container user. Nginx terminates TLS, forwards the original host and HTTPS scheme, and serves only collected static files. It intentionally does **not** expose `MEDIA_ROOT`: customer artwork and proofs must remain private. Enable private S3-compatible storage for production media and serve customer files through the authenticated download views or short-lived signed URLs.

For first staff access, create the superuser and role groups, assign staff membership, then complete TOTP enrollment:

```sh
docker compose --env-file .env -f docker-compose.prod.yml run --rm web python manage.py createsuperuser
docker compose --env-file .env -f docker-compose.prod.yml run --rm web python manage.py setup_staff_roles
```

## Wholesale catalog import (supplied distributor PDFs)

The two supplied wholesale catalogs (América Foods feb-2022, Distribuidora
Latinoandina 2024) are imported as **inactive individual retail units** — no
prices are invented, so every imported row ships with `base_price=0`,
`is_active=False` and `stock=0`:

```sh
# from the project root with the PDFs in place (see --america-pdf/--latinoandina-pdf)
python manage.py import_wholesale_catalogs --dry-run
python manage.py import_wholesale_catalogs
```

The command is idempotent (re-runs skip existing `sku` codes and
name/size duplicates across both catalogs) and attaches América Foods
product photos where they can be positionally matched. Afterwards, price
each row in the catalog admin (`base_price` with 21% IVA included, `stock`,
verified `origin_country`) and flip `is_active` to publish it. Categories
with no active products stay hidden from the homepage tiles automatically.

Run the same command in production after migrations (copy the two PDFs to
the server or pass explicit paths) so Postgres holds the same catalog.
Imported photos land under `media/catalog/products/` — keep them inside the
private-media backup set.


Open the configured private admin URL over HTTPS. Keep superuser membership limited to operators responsible for role assignment and account recovery. See [admin-security.md](admin-security.md) for role scopes and TOTP recovery configuration.

## Operations

- Verify `/healthz/`, TLS renewal, the sitemap, and the production CSP after deployment.
- Take encrypted PostgreSQL backups before migrations and on a scheduled basis; test restores regularly.
- Back up private media and the TOTP encryption key separately. Restrict access to audit logs and backups.
- Monitor web and Celery logs, PostgreSQL capacity, Redis availability, queue age, and low-disk alerts.
- Pin and promote the same image tag through staging and production. Keep the previous image tag available for rollback.
- On rollback, restore the previous image. Only reverse a database migration when its reverse operation is safe and tested; otherwise deploy a forward repair.
- Do not run the development `docker-compose.yml` on the public internet; it uses Django's development server and development-oriented defaults.
